# RecoverAI — Diagnosis Layer (Step 3)

## 1. Scope
This layer implements **DIAGNOSE only**: given a case, it produces facts +
root cause + risk factors + positive signals + a predicted recovery
probability + a confidence estimate + grounded evidence. It does **not**
select an action, check guardrails, call Razorpay, or claim anything was
recovered. Those are later stages.

## 2. Files
```
recoverai/diagnosis/
  feature_config.py     allowlist/blocklist — single source of truth for what the model may see
  train_model.py         trains + evaluates the recoverability classifier
  diagnose.py             DiagnosisEngine — structured per-case diagnosis output
  test_diagnosis.py        17 tests covering schema, leakage, reproducibility, invalid input
  model.joblib              trained pipeline (preprocessing + classifier), generated by train_model.py
  metrics_report.json        full evaluation report, generated by train_model.py
  README.md                   this file
```

## 3. Feature contract
**Pre-decision features (allowed, `PRE_DECISION_FEATURES` in `feature_config.py`):**
`leakage_category`, `amount_at_risk`, `payment_method`, `failure_reason`,
`checkout_started`, `checkout_completed`, `subscription_status`, `mandate_status`,
`invoice_status`, `days_overdue`, `retry_count`, `previous_attempt_count`,
`customer_purchase_count`, `customer_success_rate`, `customer_lifetime_value`,
`previous_payment_behavior`, `customer_opt_out`, `suspicious_flag`,
`communication_allowed`, `historical_recovery_behavior`.

**Excluded (not forbidden, just not modeled — identifiers/redundant):**
`case_id`, `transaction_id`, `customer_id`, `timestamp`, `invoice_due_date`,
`event_type` (1:1 with `leakage_category`), `payment_status` (1:1 with `leakage_category`).

**Forbidden (`ALL_FORBIDDEN_COLUMNS` — enforced in code via `assert_no_forbidden_columns`):**
`ground_truth_recoverable`, `ground_truth_recovery_outcome`, `ground_truth_recovery_value`,
`amount_recovered`, `recovery_observed`, `recovery_reason`, `predicted_recovery_likelihood`
(the model's own output — forbidding it as an input prevents accidental circularity).

`select_pre_decision_features()` is the *only* sanctioned way any code in this
package slices features, and it only ever selects columns from the allowlist —
so a forbidden column present in a dataframe simply can't reach the model,
regardless of what else is in that dataframe.

## 4. Target
`TARGET_COLUMN = ground_truth_recoverable` (bool), sourced from Step 2 ground
truth. This is standard supervised learning: the target legitimately comes
from ground truth for training purposes; it is never a model input.

**Population used for training/evaluation: leakage cases only** (`amount_at_risk`
> 0; i.e. `leakage_category != "successful"`). Recoverability is undefined for
a case with nothing at risk, so successful cases are excluded from model
training and evaluation — but `DiagnosisEngine.diagnose()` still handles them
gracefully at inference time (see §9), returning a `not_applicable` diagnosis
without invoking the model, exactly as tested in
`test_successful_case_processed_gracefully`.

Leakage-case counts by split: train 434, validation 90, test 74 (out of 719/148/133
total rows per split — see Step 2 `data/README.md`).

## 5. Model
**Selected: Logistic Regression** (`sklearn.linear_model.LogisticRegression`,
`max_iter=1000`, `random_state=42`), inside a `ColumnTransformer` + `Pipeline`
that log-transforms and scales skewed numeric features, imputes missing
values (median for numeric, most-frequent for booleans, constant `"missing"`
for categoricals), and one-hot encodes categoricals (`handle_unknown="ignore"`
so an unseen category at inference time degrades gracefully instead of
crashing).

**Why this model:** Logistic Regression was compared against a Random Forest
(`n_estimators=200, max_depth=6`) on the validation set:

| Model | Validation ROC-AUC | Validation PR-AUC |
|---|---|---|
| Logistic Regression | 0.705 | 0.854 |
| Random Forest | 0.692 | 0.854 |

Selection rule: prefer Logistic Regression for explainability (coefficients
map directly and linearly to features — see §10) unless Random Forest beats
it by more than 0.03 validation ROC-AUC. It didn't, so Logistic Regression was
selected. This is also appropriate given the modest training set size (434
leakage cases) — a linear model is less prone to overfitting than a deeper
ensemble on this amount of data.

The model is deterministic and reproducible: identical `SEED=42` runs of
`train_model.py` from a clean copy of the project produce byte-identical
`test_metrics_at_threshold` across three independent runs (verified).

## 6. Training / validation / test discipline
- **Train** (434 cases): pipeline fitting only.
- **Validation** (90 cases): used for (a) comparing Logistic Regression vs.
  Random Forest, and (b) selecting the operating threshold (§7). Never used
  for final reported performance.
- **Test** (74 cases): touched **exactly once**, after the model and
  threshold were both locked from train/validation only. `test_diagnosis.py::
  test_threshold_selected_on_validation_not_test` asserts this structurally —
  the threshold applied to test must equal the one chosen from validation.

## 7. Threshold selection
Method: sweep `sklearn.metrics.precision_recall_curve` on validation
predictions, choose the threshold that maximizes F1.

- Chosen threshold: **0.4357**
- Validation F1 at that threshold: **0.880** (precision 0.795, recall 0.985)
- Comparison at a naive 0.5 threshold (validation): F1 0.871 (precision 0.800,
  recall 0.955) — close, confirming the F1-optimal threshold isn't an
  artifact of an unstable sweep.

## 8. Final test-set metrics (touched once, reported honestly)
| Metric | Value |
|---|---|
| Precision | 0.806 |
| Recall | 1.000 |
| F1 | 0.892 |
| ROC-AUC | 0.615 |
| PR-AUC | 0.856 |

Confusion matrix (n=74): TN=2, FP=14, FN=0, TP=58.

**Honest caveat:** validation ROC-AUC (0.705) and test ROC-AUC (0.615) diverge
more than ideal. With only 74 test cases and a ~78% positive rate, ROC-AUC has
high variance at this sample size — a handful of hard cases meaningfully move
the number. PR-AUC (0.856) is more stable here and more relevant given the
class imbalance. This gap is reported rather than smoothed over; **it should
be treated as a signal to re-evaluate once real usage data exists, not as a
solid production-grade number.**

## 9. Precision/recall trade-off (why this matters for a revenue-recovery agent)
At the F1-optimal threshold, the model achieves recall = 1.0 on this test
split — it flags essentially every actually-recoverable case — at the cost of
precision 0.806 (roughly 1 in 5 flagged cases will not actually recover).

For this system, that trade-off direction is defensible **for now**: a false
negative (missing a genuinely recoverable case) is a guaranteed lost
opportunity, while a false positive mostly costs a low-value, bounded action
(reminder, payment link, or retry — see Step 1 guardrails) rather than
guaranteed loss. High recall is closer to what the business wants — but this
is a design bias, not a mathematically forced outcome, and Step 6's guardrail
engine (not this layer) is where the *cost* of acting on a false positive
actually gets bounded. This layer's job is only to surface an honest
probability + confidence; it does not decide to act.

## 10. False-positive cost analysis
- False positives on test set: **14**
- Total `amount_at_risk` associated with false positives: **₹131,732.05**
- Average false-positive amount: **₹9,409.43**
- **Assumption (stated explicitly, not fabricated as a rupee cost):** this
  reports *exposure* — the amount_at_risk attached to cases the model
  incorrectly flagged as recoverable — not a computed monetary cost, because
  no per-action cost is defined until Step 4 (action toolbox) and Step 6
  (guardrails). Reporting a fabricated ₹ cost here would violate the
  no-fabrication rule; reporting exposure instead is honest and still useful.

| failed_payment | 16 | 0.938 | 1.000 | 0.968 | 0.533 |
| failed_subscription | 17 | 0.875 | 1.000 | 0.933 | 0.905 |

Reported honestly: **failed_payment and checkout_abandonment have weak
ROC-AUC (~0.53-0.54) on test** — close to chance-level ranking, even though
F1/precision look reasonable (driven largely by the high positive base rate
in those subsets, not genuine discriminative power). **failed_subscription
and overdue_receivable show much stronger ranking ability** (ROC-AUC 0.79-0.91).
This is a real limitation, not smoothed over: at present, the model's
probability estimates are considerably more trustworthy for subscription and
receivable cases than for payment-failure and abandonment cases. Per-category
subset sizes here (16-21 cases) are small, so these numbers should be treated
as directional, not final.

## 12. Explainability approach
Logistic Regression coefficients on standardized/encoded features, extracted
directly from the fitted pipeline. Top drivers (by |coefficient|):

| Feature | Coefficient | Direction |
|---|---|---|
| `communication_allowed` | +2.150 | strongest positive driver |
| `suspicious_flag` | -1.115 | strong negative driver |
| `customer_opt_out` | -1.029 | strong negative driver |
| `failure_reason = authentication failure` | +0.633 | positive (context-dependent) |
| `retry_count` | -0.441 | negative |
| `customer_success_rate` | +0.324 | positive |

These directions are consistent with the Step 2 ground-truth generation
mechanism (`simulate_recovery()` in `data/generate_dataset.py`), which is a
useful sanity check that the model learned genuine structure rather than
noise. Per-case explanations (`root_cause`, `risk_factors`,
`positive_recovery_signals`, `evidence`) are separately generated by
rule-based extractors in `diagnose.py` that reference only fields actually
present on that case — never the model's internal coefficients, and never a
post-action field (enforced by
`test_evidence_only_references_pre_decision_fields`).

## 13. Confidence definition (distinct from predicted_recovery_likelihood)
`predicted_recovery_likelihood` answers "how likely is recovery" (the model's
probability output). `diagnosis_confidence` answers "how reliable is this
diagnosis" and is computed as:

```
base_confidence = 2 * |p - 0.5|        # distance from maximal uncertainty
if any categorical field value is unseen in training:
    confidence = base_confidence * 0.7  # extrapolation penalty
else:
    confidence = base_confidence
```

**Explicit assumption:** this is a margin-from-midpoint heuristic, not a
calibrated statistical confidence interval — the model was not calibrated
(e.g. via Platt scaling or isotonic regression) in Step 3. This is documented
as a limitation, not hidden.

## 15. Leakage tests
`test_diagnosis.py` includes explicit structural leakage tests:
- `test_forbidden_fields_never_selected` — the allowlist and forbidden list
  are disjoint; the guard function raises on forbidden input.
- `test_select_pre_decision_features_excludes_ground_truth` — slicing any
  dataframe through the sanctioned function never yields a ground-truth column.
- `test_threshold_selected_on_validation_not_test` — structurally confirms
  the threshold applied to test was the one chosen from validation.
- `test_evidence_only_references_pre_decision_fields` — every evidence entry
  in a real diagnosis output is checked against the allowlist.

All 17 tests pass (`python3 -m pytest test_diagnosis.py -v`).

## 16. Limitations
- Test-set ROC-AUC (0.615) is meaningfully below validation ROC-AUC (0.705);
  attributed to small test-set size and high variance, not investigated further
  in Step 3 — flagged for re-evaluation once more data or real usage exists.
- failed_payment and checkout_abandonment show near-chance ROC-AUC on this
  test split (§11) — the model's ranking ability is weak for these categories
  specifically, even though threshold-based F1 looks acceptable.
- Confidence is a heuristic margin measure, not a calibrated probability interval.
- False-positive cost is reported as exposure (₹ amount_at_risk), not a
  computed monetary cost, since no per-action cost model exists yet.
- The dataset's ~74-78% positive base rate pushes any F1-maximizing threshold
  toward high recall / moderate precision — this is a property of the
  synthetic ground-truth design (see `data/README.md` limitations), not
  something Step 3 can fix.
- No categorical feature interactions beyond what one-hot + linear
  coefficients naturally capture; a tree-based model was tried but not
  selected (see §5).

## 17. What is ready for Step 4
- `DiagnosisEngine.diagnose(case)` is a stable, tested interface returning a
  structured dict with `predicted_recovery_likelihood`, `diagnosis_confidence`,
  root cause, risk factors, positive signals, and evidence — everything the
  Step 4 action toolbox and Step 5 decision engine need as input, with no
  action-selection or guardrail logic mixed in.
- The feature contract (`feature_config.py`) is reusable as-is by later
  layers that need to know what is/isn't a legitimate pre-decision signal.
